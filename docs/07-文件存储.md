# 07 - 文件存储

> 状态：文件库已落地（images 表）· 最后更新：2026-08-26

## 1. 设计约束

- 上传图与输出图都**很大**（几百 MB 级），不能频繁搬运，按 id 固定居
- Docker 部署时文件目录需**映射到宿主机**（volume），容器重建不丢数据
- 网页展示**全部用缩略图**，原图不进页面（见 `03-整体架构` 3.4）
- 元数据（创建时间、文件名、id 等）用 **SQLite** 记录，便于检索

## 2. 目录结构

`data/library/` 为文件库根目录，Docker 部署时整体映射出去。

```
data/
└── library/                        # 文件库根目录（Docker volume 映射）
    ├── library.db                  # SQLite 元数据记录
    └── images/                     # 图片存放目录
        ├── {id1}/                  # 每张图一个文件夹，文件夹名 = 图片 id
        │   ├── original.xxx        # 原尺寸图（用于处理）
        │   └── thumb.webp          # 缩略图（用于前端展示）
        ├── {id2}/
        │   ├── original.xxx
        │   └── thumb.webp
        └── ...
```

### 2.1 为什么按 id 建文件夹

- id 唯一，文件夹不会重名
- 单张图的所有派生文件（原图、缩略图、将来可能的中间产物）集中在一个文件夹
- 避免单目录文件数过多（大图场景文件数虽不多，但按文件夹隔离便于管理与清理）

### 2.2 文件命名

- **文件夹名**：图片 id（如 `a3f9...`），唯一
- **原图**：保留上传原文件名与扩展名，如 `original.jpg` / `original.png` / `original.tif`
  > 保留扩展名以便按格式区分；文件名统一 `original.<ext>`，原始文件名记入元数据
- **缩略图**：统一 `thumb.webp`（体积小、质量够、浏览器原生支持）

## 3. SQLite 元数据（library.db）

记录每张图片的基本信息。表结构 `images`：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | 主键，唯一 id |
| `original_name` | string | 上传时的原始文件名 |
| `stored_name` | string | 落盘文件名（`original.<ext>`） |
| `format` | string | 格式（png/jpg/tif/psd） |
| `width_px` | int | 原图宽 |
| `height_px` | int | 原图高 |
| `dpi` | int | 原图 DPI |
| `mode` | string | 色彩模式（RGB/CMYK/灰度） |
| `size_bytes` | int | 文件大小 |
| `source` | string | 来源：`upload`（用户上传）/ `prepress`（印前生成）/ `impose`（排版输出） |
| `ref_type` | string | 关联类型（若为生成产物，关联的 type_id） |
| `ref_size` | string | 关联尺码（若为印前产物，关联的 size_id） |
| `task_id` | string | 关联任务 id（若由任务产生） |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 最后编辑时间 |

### 3.1 检索

- 按来源、类型、尺码、时间范围筛选
- 文件库页面按 `created_at` 倒序展示缩略图

## 4. 缩略图

### 4.1 生成时机

- **上传时**：原图落盘后立即生成缩略图
- **生成产物入库时**：PSD/TIF 产物同样生成缩略图（合成平面预览）

### 4.2 规格（可配置）

缩略图规格由配置文件 `configs/storage/storage.json` 定义，当前默认值：

| 项 | 默认值 | 说明 |
|----|--------|------|
| 格式 | `webp` | 体积小，浏览器原生支持 |
| 最长边 | `400` px | 按原图宽高比缩放，定比 |
| 质量 | `80` | 预览用，够看即可 |

`configs/storage/storage.json` 示例：

```json
thumbnail:
  format: webp
  max_size_px: 400      # 最长边像素
  quality: 80
```

> 缩略图规格与 `05-页面与交互` 实时预览的定比缩略图统一，共读此配置。后续若需分档（列表/详情），可扩展为 `thumbnail.list` / `thumbnail.detail`。

### 4.3 任务并发上限

`storage.json` 的 `tasks.max_concurrency` 限制**同时运行**的任务数（默认 2）：

```json
tasks:
  max_concurrency: 2      # ≥1，并行任务上限
```

- 调度器（`app/web/tasks.py`）统一派发：`submit` 把任务入队（`pending`），调度线程按 `max_concurrency` 拉起 worker，超出的任务排队等待。
- 上限**动态读配置**：通过 `PUT /api/config/storage/tasks`（body `{max_concurrency}`）修改后落盘 + `reload_all()`，无需重启即对新派发生效（运行中的任务不受影响）。
- 配置页 `/config/storage` 提供在线编辑入口。

### 4.4 生成方式

- Pillow 生成（轻量 I/O，缩略图尺寸小，Pillow 足够）
- 大图缩略图：按比例降采样，不全量载入内存（用 PIL 的 `Image.draft` 或 pyvips `thumbnail_image`）

## 5. 图片 id

- 唯一 id，用于文件夹名与元数据主键
- 生成方式：**ULID**（可按时间排序，文件库按时间浏览更友好；且全库唯一不重复）
- 全局唯一

## 6. 文件库与任务的关系

| 任务类型 | 产物 | 入库 |
|---------|------|------|
| 印前生成 | 分层 PSD | ✅ 入文件库（原图+缩略图） |
| 排版 | 平面 TIF（带 alpha） | ✅ 入文件库 |
| 上传 | 原图 | ✅ 入文件库（供印前/排版取用） |

- 上传图、印前产物、排版产物**统一存入文件库**，按 `source` 字段区分
- 排版页可从文件库选图（`source=prepress` 的产物），也可新上传
- 任务记录（`06` 的 SQLite）独立于文件库 DB，通过 `task_id` 关联

## 7. 存储分离与 DB 合并

```
data/library/
├── library.db        # 元数据 + 任务记录 + 任务日志（结构化，小）
└── images/{id}/      # 图片文件（大，二进制）
```

- **元数据**（SQLite）与**二进制文件**（图片）分离
- 图片按 id 文件夹存储，DB 只存路径与信息，不存图片数据
- **DB 合并**：任务记录、任务日志、文件库元数据统一存入 `library.db`，减少 DB 数量
  - `images` 表：文件库元数据
  - `tasks` 表：任务记录
  - `task_logs` 表：任务级日志
- **写入方**：`tasks` / `task_logs` 由调度器经 `signal.emit` / `signal.log` 写入（见 `06` §4.2、§10）；任务脚本本身不直接写 DB
- Docker 部署：`data/library/` 整体映射到宿主机卷（DB + 图片一同持久化）

## 9. 开放问题

1. **清理策略**：是否需要自动清理（按保留期/容量上限）？
2. **原图保留**：印前生成的上传原图是否也入库保留，还是只留产物？
3. **中间产物**：生成过程中的中间文件（如主色提取临时图）是否落盘，还是只在内存？
4. **缩略图分档**：当前单档 400px，后续是否按列表/详情分多档？
