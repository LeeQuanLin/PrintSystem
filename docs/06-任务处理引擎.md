# 06 - 任务处理引擎

> 状态：规划中 · 最后更新：2026-08-26
> 核心设计：**插件式调度器**。调度器只管分配/调度/状态收集/推送，不关心具体任务怎么做；每种任务是一个面向对象的 Python 类，放在约定目录下作为"脚本"，调度器动态加载。

## 1. 设计目标

印前生成与排版都是**长耗时、重资源**操作，且未来可能新增其他任务类型（如批量导出、质检报告）。为不阻塞前端并支持任务类型扩展，本引擎遵循**开闭原则**：

| 目标 | 实现 |
|------|------|
| **加任务类型不改调度器** | 每种任务是一个 Python 类，放 `app/tasks/scripts/`，调度器 importlib 扫描注册 |
| **调度器零业务知识** | 调度器不 import 业务模块，只认 `BaseTask` 契约与 `TYPE` 注册表 |
| **状态上报解耦** | 任务通过回调 `signal.emit()` 上报，不持有调度器引用，不直接写 DB / 推 WebSocket |
| **不阻塞前端** | 提交即入队返回，Worker 线程池后台执行，WebSocket 实时推送进度 |
| **重启不丢任务** | 任务记录落 SQLite，重启后 `pending` 重新入队、`running` 重置为 `pending` |

```
前端提交 ──▶ Scheduler 入队 ──▶ Worker 线程池取任务
                                     │
                                     ▼
                               registry 按 type 查 Task 类
                               实例化 → 注入 TaskContext + Signal
                                     │
                                     ▼
                               task.run(ctx, signal)
                                     │ signal.emit(stage, progress, msg)
                                     ▼
                               Scheduler 收状态 ──▶ WebSocket 推前端
                               同时写 SQLite（tasks / task_logs）
```

## 3. 任务脚本契约（BaseTask）

所有任务类型必须继承 `BaseTask`，定义于 `app/tasks/base.py`。

### 3.1 接口定义

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass(frozen=True)
class TaskContext:
    """任务上下文（不可变），由调度器注入"""
    task_id: str
    task_type: str
    params: dict           # 任务参数（印前: type_id/size_id/images/overrides；排版: preset_id/slots）
    workdir: str           # 任务工作目录（中间产物临时存放）
    library_root: str      # 文件库根目录（产物入库目标）

@dataclass
class TaskResult:
    """任务返回值"""
    outputs: list[dict]    # 产物列表 [{image_id, path, ...}]
    summary: str           # 完成摘要

class BaseTask(ABC):
    """任务基类。每种任务类型继承并实现 run()。"""

    TYPE: str = ""         # 任务类型标识，必须由子类覆盖，如 "prepress" / "impose"

    @abstractmethod
    def run(self, ctx: TaskContext, signal: "Signal") -> TaskResult:
        """
        执行任务。

        Args:
            ctx: 任务上下文（不可变）
            signal: 状态回调，任务在关键节点调用 signal.emit / signal.log

        Returns:
            TaskResult，含产物信息

        Raises:
            TaskError: 任务失败时抛出，调度器捕获置 failed
        """
```

### 3.2 契约约定

| 约定 | 说明 |
|------|------|
| `TYPE` 唯一 | 每个子类的 `TYPE` 必须全局唯一，启动时 registry 校验冲突则拒绝启动 |
| `run` 内禁止直接 IO | 不允许 `run` 内直接写 SQLite 或推 WebSocket，**全部经 `signal` 上报**，由调度器统一处理 |
| 失败用 `TaskError` | 业务失败抛 `TaskError(reason)`；其他异常视为系统错误，调度器一并捕获置 `failed` |
| 不持有调度器引用 | 任务只持有 `signal` 对象，不持有 `Scheduler`，避免反向耦合 |
| 产物入库经 `library_root` | 任务把产物写到 `ctx.library_root/{image_id}/`，元数据由调度器在 `succeeded` 时登记 |

## 4. 信号机制（Signal）

`Signal` 是调度器注入给任务的**单向回调对象**，任务用它向调度器上报状态。

### 4.1 接口

```python
class Signal:
    """任务状态回调。由调度器构造，绑定到具体 task_id。"""

    def emit(self, stage: str, progress: int, message: str) -> None:
        """
        上报进度。

        Args:
            stage: 阶段名（如 "预检" / "处理图片区" / "组装 PSD"）
            progress: 0-100 进度百分比
            message: 详情（如 "FaceA 适配完成 1494×1994"）
        """

    def log(self, level: str, message: str) -> None:
        """
        写任务级日志。

        Args:
            level: "INFO" / "WARNING" / "ERROR"
            message: 日志内容
        """
```

### 4.2 调度器侧处理

收到 `signal.emit` 后，调度器同步执行三件事：

1. **更新内存任务状态**：`progress` / `stage` 写入任务对象
2. **写 SQLite**：更新 `tasks` 表 `progress`，追加 `task_logs` 一条记录
3. **WebSocket 广播**：推 `task_progress` 事件给所有连接的前端

收到 `signal.log` 后：只写 `task_logs` 表（不更新进度、不推 WebSocket）。

### 4.3 为什么用回调而非标准库 signal

- Python `signal` 模块限 Unix 且不跨线程，Worker 线程内不可用
- `asyncio.Event` 不能携带数据（stage/progress/message）
- 回调对象简单、类型安全、同步执行，与线程池模型天然契合

## 5. 任务上下文（TaskContext）

`frozen=True` 的 dataclass，**不可变**，避免任务修改上下文影响调度器。

| 字段 | 类型 | 说明 |
|------|------|------|
| `task_id` | str | 任务唯一 ID（ULID） |
| `task_type` | str | 任务类型，对应 `BaseTask.TYPE` |
| `params` | dict | 任务参数，结构由任务类型自定义 |
| `workdir` | str | 任务工作目录，中间产物临时存放，任务结束可清理 |
| `library_root` | str | 文件库根目录，最终产物入库目标 |

### 5.1 params 结构（按类型）

**印前生成**（`task_type="prepress"`）：
```json
{
  "type_id": "quilt_ab",
  "size_id": "200x230",
  "images": {"FaceA": "01JX...", "FaceB": "01JY..."},
  "overrides": {"FaceA": {"scale": 1.05}}
}
```

**排版**（`task_type="impose"`）：
```json
{
  "preset_id": "double_bedsheet",
  "slots": [
    {"image_id": "01JX...", "rotation": 0},
    {"image_id": "01JY...", "rotation": 180}
  ]
}
```

> `images` / `slots` 中的 `image_id` 是文件库中已入库图片的 ULID，任务脚本按 id 从 `library_root` 载入。

## 6. 调度器（Scheduler）

`app/tasks/scheduler.py`，单例，进程内唯一。

### 6.1 职责

| 职责 | 说明 |
|------|------|
| 队列管理 | FIFO 内存队列 + SQLite 持久化，重启恢复 |
| 注册表 | 启动时扫描 `scripts/` 建 `type → Task class` 映射 |
| Worker 池 | `ThreadPoolExecutor`，并发上限可配置（默认 2） |
| 状态收集 | 接收 `signal.emit/log`，更新状态 + 写 DB + 推 WebSocket |
| 生命周期 | 启动加载未完成任务、停止时优雅 drain |

### 6.2 Worker 循环

```
while running:
    task = queue.get()              # 阻塞取任务
    TaskClass = registry[task.type]
    instance = TaskClass()
    ctx = TaskContext(task_id, task.type, task.params, workdir, library_root)
    signal = Signal(task_id, on_emit, on_log)   # 绑定回调
    置 task.status = "running"
    try:
        result = instance.run(ctx, signal)
        置 task.status = "succeeded", 写产物元数据
    except TaskError as e:
        置 task.status = "failed", error = e.reason
    except Exception as e:
        置 task.status = "failed", error = "系统错误: " + str(e)
    finally:
        清理 workdir
```

### 6.3 并发控制

- 并发上限由 `configs/storage/storage.json` 的 `queue.concurrency` 配置，默认 `2`
- 超出并发的任务保持 `pending` 排队
- 大图处理耗内存，建议生产环境按可用内存调整（见 `08` §7 监控）

### 6.4 重启恢复

启动时从 SQLite `tasks` 表加载：

| 原 status | 恢复动作 |
|-----------|---------|
| `pending` | 重新入队 |
| `running` | 重置为 `pending` 重新入队（重启即中断，需重跑） |
| `succeeded` / `failed` | 保持状态，仅展示 |

## 7. 任务状态机

```
pending ──▶ running ──▶ succeeded
              │
              └──▶ failed ──▶ (重试新建任务)
```

| 状态 | 触发 |
|------|------|
| `pending` | 提交入队 |
| `running` | Worker 取出，调 `run` 前 |
| `succeeded` | `run` 正常返回 `TaskResult` |
| `failed` | `run` 抛 `TaskError` 或任何异常 |

状态转换由调度器驱动，任务脚本本身不操作状态。

## 8. 任务类型注册与发现（Registry）

`app/tasks/registry.py`，启动时扫描 `app/tasks/scripts/` 目录。

### 8.1 注册流程

```
1. 扫描 scripts/*.py
2. importlib 动态导入每个模块
3. 找模块内继承 BaseTask 的 Task 类
4. 读 Task.TYPE，校验全局唯一（冲突则启动失败）
5. 建 {TYPE: TaskClass} 注册表
```

### 8.2 脚本目录约定

```
app/tasks/scripts/
├── prepress.py    # class PrepressTask(BaseTask): TYPE = "prepress"
├── impose.py      # class ImposeTask(BaseTask):   TYPE = "impose"
└── <新类型>.py     # 新增任务类型只需新建一个 .py
```

每个脚本模块必须暴露：
- 一个继承 `BaseTask` 的类（类名建议 `XxxTask`）
- 类常量 `TYPE`（ASCII 唯一标识）

### 8.3 新增任务类型步骤

1. 在 `app/tasks/scripts/` 新建 `xxx.py`
2. 定义 `class XxxTask(BaseTask)`，设 `TYPE = "xxx"`
3. 实现 `run(self, ctx, signal) -> TaskResult`
4. 重启服务即生效

**调度器代码零修改**——这是本架构的核心目标。

```json

  "type": "prepress",
  "params": {
    "type_id": "quilt_ab",

    "images": {"FaceA": "01JX...", "FaceB": "01JY..."},
```

## 13. 失败与重试

- 任务失败时调度器捕获异常，置 `failed`，写 `error` 字段
- `TaskError` 为业务失败（如预检不达标、配置错误），`error` 直接展示
- 其他异常视为系统错误，`error = "系统错误: " + str(e)`，同时 ERROR 级日志落 `logs/app.log`
- 重试：创建新任务记录（新 task_id），原图与中间文件不丢，基于已有输入重跑
- 连续失败 N 次告警（待定，见开放问题）

## 14. 日志

两层日志，见 `08-部署与运维` §4。

### 14.1 任务级日志

- 由 `signal.log` / `signal.emit` 触发，落 `task_logs` 表
- 页面任务详情展示完整处理链路（阶段时间线 + 日志条目）

### 14.2 系统日志

- 进程级日志写 `logs/app.log`，按日滚动

## 15. 执行模型选型说明

**线程池（ThreadPoolExecutor）** 而非 asyncio：

- **pyvips 是 C 扩展**：调用时释放 GIL，多线程能真并行处理图像
- **CPU 密集型**：图像处理是 CPU 密集，asyncio 对 CPU 密集无优势，反而需 `run_in_executor` 绕回线程池
- **同步生态简单**：SQLite、Pillow、psd-tools 均同步 API，线程池直调最简单
- **FastAPI 共存**：FastAPI 主事件循环跑 async 路由与 WebSocket，任务执行独立线程池，互不阻塞

> 若未来出现大量 IO 等待型任务（如远程下载图件），可再评估混合模型。本期单机 Docker，线程池足够。

## 16. 开放问题

1. **脚本热加载**：新增/修改 `scripts/*.py` 是否支持不重启生效？当前需重启
2. **任务取消**：`running` 任务是否支持取消？线程池内强杀需配合 `signal` 协作式取消
3. **优先级插队**：是否支持加急单插队？当前纯 FIFO
4. **任务超时**：大图处理超时（如 16bit 大画布）如何处理？是否每类任务配超时阈值
5. **连续失败告警**：N 次失败后是否自动告警或熔断该类型
6. **并发按类型分配**：是否对不同任务类型设独立并发上限（如排版比印前更耗内存）
7. **任务保留期**：`succeeded` 任务产物与记录保留多久？自动清理策略
